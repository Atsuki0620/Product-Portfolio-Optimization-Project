## 2. 優先度マトリクスによる問題分類

各問題を「ビジネスインパクト」と「実装難易度」の2軸で評価し、優先度を決定します。

### 2.1 優先度分類の定義

**ビジネスインパクト**:
- **高**: 粗利改善、実行可能性、リスク軽減に直結
- **中**: 保守性、実行速度の改善
- **低**: 将来的な拡張性、利便性の向上

**実装難易度**:
- **容易**: 1週間以内に実装可能
- **中程度**: 1〜4週間で実装可能
- **困難**: 1〜3ヶ月で実装可能
- **非常に困難**: 3ヶ月以上かかる

### 2.2 優先度マトリクス

```
                  実装難易度
                容易  中  困難  非常に困難
        高      A    A    B      C
インパクト 中      B    B    C      D
        低      C    D    D      D

A: 最優先（即時対応）
B: 高優先（短期対応）
C: 中優先（中期対応）
D: 低優先（長期対応）
```

### 3.2 最優先問題の詳細対策

#### A-1: 戦略係数の根拠の不明確性（問題2-1）

**問題**: 現在の戦略係数（aggressive_expansion: 0.8等）が経験則で決められており、根拠が不明。

**対策**: 感度分析の結果を反映した係数の設定

| 項目 | 内容 |
|---|---|
| **原因** | パラメータが経験則で設定されており、データに基づく根拠がない |
| **推奨対策** | 感度分析結果を活用し、データドリブンな係数設定を実施 |
| **実装内容** | 1. 感度分析で得られた「達成可能シェア」と「目標シェア」の乖離を分析<br>2. Oil & Gasセグメントのように過度に保守的な設定を見直し<br>3. 係数を0.8 → 0.9〜1.0に引き上げ、実現可能性を維持しつつ粗利を最大化<br>4. 設定ファイル（config.yaml）に係数の根拠をコメントとして記載 |
| **実装難易度** | 容易（1週間） |
| **期待効果** | 総粗利の5〜10%改善、目標設定の透明性向上 |
| **リスク** | 係数が高すぎると実行不可能になる可能性あり → Step 3で検証 |

**実装例**:
```yaml
# config.yaml
strategy_coefficients:
  aggressive_expansion: 0.90  # 感度分析により、0.8では過度に保守的と判明
  maintain: 0.90
  reduction: 0.70
  withdrawal: 0.30

  # 根拠: sensitivity_analysis.pyの結果、Oil & Gasで達成可能シェア46.8%に対し
  # 目標シェア22.5%と大幅に余裕があることが判明。係数を0.8→0.9に引き上げ。
```

#### A-3: 自動調整機能の不在（問題3-1）

**問題**: 実行可能性チェックで失敗しても、目標を自動調整する仕組みがない。

**対策**: 段階的な目標引き下げループの実装

| 項目 | 内容 |
|---|---|
| **原因** | Step 3が検証のみで、調整機能を持っていない |
| **推奨対策** | 実行可能性チェック失敗時に、目標を段階的に引き下げる自動調整機能を追加 |
| **実装内容** | 1. 目標シェアが達成不可能な場合、5%ずつ引き下げ<br>2. 最大5回まで反復し、実行可能な目標を探索<br>3. 調整履歴をログファイルに記録<br>4. 最終的に実行可能な目標が見つからない場合、エラーを出力 |
| **実装難易度** | 中程度（2週間） |
| **期待効果** | 手動調整の手間削減、実行可能性の自動担保 |
| **リスク** | 過度に引き下げると、ビジネス目標から乖離 → 下限を設定 |

**実装例**:
```python
# scripts/step3_feasibility_validation.pyの拡張

def auto_adjust_targets(target_share, market_data, capacity, max_iterations=5):
    """
    目標シェアを段階的に調整し、実行可能な目標を探索する。
    """
    for i in range(max_iterations):
        is_feasible, message = check_feasibility(target_share, market_data, capacity)

        if is_feasible:
            print(f"✓ 反復 {i}: 実行可能な目標を発見")
            return target_share, True

        print(f"✗ 反復 {i}: 実行不可能 - {message}")
        print(f"  目標シェアを5%引き下げます")

        # 全セグメントの目標を5%引き下げ
        for segment in target_share:
            target_share[segment]['lower'] *= 0.95
            target_share[segment]['upper'] *= 0.95

    print(f"✗ {max_iterations}回の反復でも実行可能な目標が見つかりませんでした")
    return target_share, False

# 実行例
target_share_final, success = auto_adjust_targets(target_share, market_data, capacity)
if not success:
    raise ValueError("実行可能な目標が見つかりませんでした。入力データを確認してください。")
```

#### A-4: 最適化失敗時の診断機能不足（問題4-4）

**問題**: Infeasibleエラーが発生しても、どの制約が問題かわからない。

**対策**: 制約充足度の個別チェック機能

| 項目 | 内容 |
|---|---|
| **原因** | エラーハンドリングが最小限で、診断機能がない |
| **推奨対策** | 最適化実行前に、各制約が理論的に充足可能かを簡易チェック |
| **実装内容** | 1. 総需要下限 ≤ 総キャパシティ のチェック<br>2. セグメント別需要下限 ≤ セグメント別達成可能数量 のチェック<br>3. 矛盾がある制約を事前に警告<br>4. 具体的な緩和提案を出力（例: "キャパシティを10,000本増やすか、目標シェアを3%下げてください"） |
| **実装難易度** | 中程度（2週間） |
| **期待効果** | デバッグ時間の短縮、ユーザーへの具体的なガイダンス提供 |
| **リスク** | 簡易チェックでは検出できない矛盾もある → 完全ではないことを明示 |

**実装例**:
```python
# scripts/step4_optimization_execution.pyの拡張

def diagnose_constraints(target_share, market_data, capacity):
    """
    最適化実行前に制約の充足可能性を診断する。
    """
    total_capacity = sum(capacity.values())
    total_demand_lower = 0

    issues = []

    for segment, targets in target_share.items():
        market_size = market_data[segment]['market_size_after_3y']
        demand_lower = market_size * targets['lower']
        total_demand_lower += demand_lower

    # チェック1: 総需要下限 vs 総キャパシティ
    if total_demand_lower > total_capacity:
        shortage = total_demand_lower - total_capacity
        issues.append({
            'constraint': '総キャパシティ制約',
            'problem': f'需要下限 {total_demand_lower:,.0f}本 > キャパシティ {total_capacity:,.0f}本',
            'suggestion': f'キャパシティを {shortage:,.0f}本増やすか、目標シェアを {shortage/total_demand_lower*100:.1f}%下げてください'
        })

    if issues:
        print("=" * 80)
        print("制約診断: 以下の問題が検出されました")
        print("=" * 80)
        for issue in issues:
            print(f"\n制約: {issue['constraint']}")
            print(f"問題: {issue['problem']}")
            print(f"提案: {issue['suggestion']}")
        return False

    print("✓ 制約診断: すべての制約が理論的に充足可能です")
    return True

# 最適化実行前に診断
if not diagnose_constraints(target_share, market_data, capacity):
    raise ValueError("制約が充足できません。上記の提案を参照してください。")
```

| **実装内容** | 1. カラム名を統一: `product_code`, `plant_code`, `segment_code`<br>2. スキーマ定義書を作成（schema.md）<br>3. 各ステップのスクリプトを修正し、統一されたカラム名を使用<br>4. データバリデーション関数を追加（オプション） |
| **実装難易度** | 容易（1週間） |
| **期待効果** | バグ削減、保守性向上 |
| **リスク** | 既存コードの修正が必要 → テストを十分に実施 |

**実装例**:

#### A-6: エラー伝播の問題（問題INT-2）

**問題**: 前段のステップでエラーが発生しても、後段のステップで検出が遅れる。

**対策**: Fail-Fast原則の導入

| 項目 | 内容 |
|---|---|
| **原因** | 各ステップが独立して実行され、前段の出力検証が不十分 |
| **推奨対策** | 各ステップで異常を検出したら、即座に処理を停止 |
| **実装内容** | 1. 各ステップの最後に、出力データの品質チェックを追加<br>2. 異常値（負の値、欠損値、範囲外の値）を検出<br>3. エラーメッセージを明確に表示し、処理を停止<br>4. ログファイルにエラー詳細を記録 |
| **実装難易度** | 容易（1週間） |
| **期待効果** | デバッグ時間の短縮、エラーの早期発見 |
| **リスク** | 誤検知によって正常なデータが停止される可能性 → 検証ロジックを慎重に設計 |

**実装例**:
```python
# scripts/step1_data_preparation.pyの最後に追加

def validate_market_forecast(market_df):
    """
    市場予測データの品質チェック。
    """
    errors = []

    # チェック1: 市場規模が正の値か
    if (market_df['market_size_after_3y'] <= 0).any():
        errors.append("市場規模が0以下のレコードがあります")

    # チェック2: シェアが0〜1の範囲か
    if ((market_df['current_share'] < 0) | (market_df['current_share'] > 1)).any():
        errors.append("現状シェアが0〜1の範囲外です")

    # チェック3: 欠損値がないか
    if market_df.isnull().any().any():
        errors.append("欠損値が存在します")

    if errors:
        print("=" * 80)
        print("データ検証エラー")
        print("=" * 80)
        for error in errors:
            print(f"✗ {error}")
        raise ValueError("Step 1の出力データに問題があります。上記のエラーを修正してください。")

    print("✓ データ検証: すべてのチェックに合格しました")

# Step 1の最後に実行
validate_market_forecast(market_master_final)
```

## 9. 結論

本フレームワークは、製品ポートフォリオ最適化の基本的な機能を備えていますが、以下の課題があります：

1. **パラメータ設定の保守性**: 感度分析により、現状の設定が過度に保守的であることが判明
2. **エラーハンドリングの不足**: 診断機能が不十分で、デバッグが困難
3. **アーキテクチャの改善余地**: モジュール化、テスト、ドキュメントが不足

しかし、これらの問題は段階的に解決可能であり、**Phase 1の実装により、即座に10〜15%の粗利改善が期待できます**。

本改善提案を参考に、ビジネス要件と開発リソースに応じた実装計画を策定することを推奨します。
